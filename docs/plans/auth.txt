### Component 1 — `BrandTitle`

**Purpose:** Display the brand text in the upper-left corner of both mockups.

**Props:**

- `text`: displayed text; defaults to `"Rental Management"`.
- `href`: optional destination. When supplied, render the brand as a link.
- `className`: optional styling override.

**Visual requirements:**

- Blue brand text.
- Small, clean typography.
- Minimal styling.
- No unnecessary background, card, or decorative icon.

The component must support static text and linked text without requiring separate implementations.

### Component 2 — `HomeButton`

**Purpose:** Render the compact Home CTA shown in the upper-right corner of both mockups.

**Props:**

- `label`: configurable label; defaults to `"Home"`.
- `href`: optional navigation destination.
- `onClick`: optional callback.
- `disabled`: optional boolean.
- `className`: optional styling override.

**Visual requirements:**

- White or transparent background.
- Thin blue outline.
- Blue text.
- Fully rounded, oval-shaped appearance.
- Compact dimensions with adequate clickable space.
- Visible keyboard-focus style.
- Appropriate disabled state.

Use the existing shadcn `Button` primitive.

If `href` is provided, preserve link semantics. Do not nest an anchor element inside a button. Use an appropriate anchor or project-supported link mechanism without assuming that a particular router is installed.

Do not implement application routing or invent a destination.

### Component 3 — `AuthField`

**Purpose:** This is the primary reusable component. It must support every input field in both mockups.

Required use cases:

- Login email
- Login password
- Registration email
- Registration name
- Registration phone
- Registration password
- Confirm password

**Do not create separate custom field implementations for these seven inputs.** Configure instances of `AuthField` using props.

**Props:**

- `id`: unique input identifier.
- `name`: optional field name.
- `label`: optional field label.
- `type`: native input type, such as `"text"`, `"email"`, `"tel"`, or `"password"`.
- `placeholder`: optional placeholder text.
- `value`: optional controlled value.
- `defaultValue`: optional initial uncontrolled value.
- `onChange`: input change callback.
- `layout`: `"horizontal"` or `"stacked"`.
- `required`: optional boolean.
- `disabled`: optional boolean.
- `error`: optional validation error message.
- `autoComplete`: optional native autocomplete value.
- `endAdornment`: optional React element rendered as trailing content, such as the password-strength indicator.
- `className`: wrapper styling override.
- `labelClassName`: optional label styling override.
- `inputClassName`: optional input styling override.

Also forward appropriate standard HTML input attributes and accessibility attributes so the component remains extensible.

Do not allow `value` and `defaultValue` to be supplied simultaneously. Respect native controlled and uncontrolled input behavior.

**Layout behavior**

For `layout="horizontal"`:

- Render the label to the left of the input.
- Match the Login screenshot.
- Maintain consistent label and input alignment.
- Allow the layout to stack on smaller screens when necessary.

For `layout="stacked"`:

- Render the label above the input.
- Match the Registration screenshot.
- Maintain consistent spacing between label and input.

**Visual requirements**

- White input background.
- Thin, neutral-colored border.
- Rounded rectangular shape.
- Consistent height, typography, and spacing.
- Subtle neutral placeholder text.
- Clearly visible focus styles.
- Appropriate error and disabled states.
- Styling overrides through props.

**Accessibility requirements**

- Associate labels with inputs using `htmlFor` and `id`.
- Provide accessible validation messages.
- Apply `aria-invalid` and appropriate error-description associations when errors exist.
- Preserve keyboard navigation and native input behavior.

Use the existing shadcn `Label` and `Input` primitives.

### Component 4 — `AuthSubmitButton`

**Purpose:** Render the large, oval authentication CTA used in both mockups.

The Login screen should be able to display `"SIGN IN"`. The Registration screen should be able to display `"SIGN UP"` or `"REGISTER"` using the same component.

**Props:**

- `label`: configurable button label.
- `type`: `"button"`, `"submit"`, or `"reset"`.
- `onClick`: optional callback.
- `disabled`: optional boolean.
- `loading`: optional boolean.
- `loadingText`: optional loading label.
- `className`: optional styling override.

**Visual requirements**

- Large oval or pill-shaped button.
- Thin blue outline.
- White or transparent background.
- Dark text.
- Centered label.
- Configurable dimensions and padding through styling overrides.
- Clear hover, active, focus-visible, disabled, and loading states.

Use the existing shadcn `Button` primitive and customize its appearance to match the mockup.

Support native button behavior. Respect the `type` prop and do not hardcode every CTA to submit.

The component must not perform authentication, call APIs, navigate automatically, or contain application-specific business logic.

### Component 5 — `AuthLink`

**Purpose:** Render the reusable blue text links beneath authentication CTAs.

Required examples:

- `"Register here"`
- `"Forgot username / password"`
- `"Login"`

**Props:**

- `label`: displayed link text.
- `href`: optional URL or application path.
- `onClick`: optional click callback.
- `className`: optional styling override.

**Visual requirements**

- Blue text.
- Minimal decoration.
- Suitable for inline placement inside supporting account-related text.
- Visible keyboard-focus style.
- No button-like background or border by default.

Use semantic anchor elements for navigation. Do not use a fake `href="#"` when no destination has been supplied.

Allow a suitable callback for non-navigation actions without converting every link into a button.

Do not implement routing, account recovery, or registration logic.

### Component 6 — `PasswordStrengthIndicator`

**Purpose:** Display the compact password-strength meter shown toward the right side of the Registration password field.

**Props:**

- `strength`: one of `"empty"`, `"weak"`, `"medium"`, or `"strong"`.
- `showLabel`: optional boolean controlling whether a strength label is shown.
- `className`: optional styling override.

The indicator must derive its visual state from the supplied `strength` prop. When a parent updates the prop, the rendered indicator must update accordingly.

**Visual requirements**

- Compact horizontal indicator.
- Visually distinguish weak, medium, and strong states.
- Use a neutral appearance when the strength is empty.
- Fit into the password field's trailing region without obstructing entered text or making the field excessively tall.
- Reuse the existing shadcn `Progress` primitive where appropriate.

If the Progress primitive does not directly support the needed visual states, customize the indicator while preserving accessibility and avoiding unnecessary dependencies.

Do not implement authentication, password storage, backend validation, or a separate password-security system.

Do not claim that the meter guarantees password security.

Keep the component independently reusable. It must not depend on `AuthField` or any page component.
